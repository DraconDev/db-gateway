## Verdict

The **core is in unusually good shape for a personal project**: bounded
SQLite execution, authorizer-based read-only/scoped-key enforcement,
generation-bound credentials, idempotent writes with lost-ack discipline,
safe lifecycle (clone/export/import/tombstone-purge), backup freshness +
digest watchdog, and a large, green, adversarial test suite. No TODO/FIXME
debt in `src/`; exactly one `unsafe` block (`libc::kill` in
`src/main.rs:426`, companion shutdown).

The risk has moved **outside the core**: status documents contradict each
other and the newer evidence, the off-host backup story has a silent
coverage gap for new databases, one production unit exists only on the
host (not in the repo), and the Turso migration — the project's stated
purpose — is still blocked on unverified remote facts and a missing Rust
client path. Nothing below requires weakening any existing contract.

  **What was verified, without reading the secret values.** The two
  credentials live in `~/.dracon` (the `dracon-home` repo) as
  `secrets/aws/devdrac-access-keys-20260829.csv` and
  `secrets/cloudflare.env` — they are *not* db-gateway's OVH/Litestream
  material, and the bucket's SSE-C encryption does not cover them (it
  protects backup objects in OVH S3, not credentials in a git repo).
  The containing repo is **private on both remotes** (GitHub:
  `isPrivate=true` via the authenticated API; GitLab: anonymous requests
  are redirected to sign-in, SSH access needs the owner's key). The
  credential values were then matched against the working tree *and the
  full history* of all ten sibling repos on this box: **zero hits** —
  the exposure is confined to the one private repo. Both credentials are
  still live (the AWS key authenticates as IAM user `dracondev` in
  account 827650156510; the Cloudflare token reports `status=active`,
  `expires_on=never`, scoped to zone `dracon.uk` DNS/Edit), so this is
  a live-credential-in-a-private-repo situation, not an inert one.

  **The owner's decision (2026-10-19): do not rotate.** Basis: the
  containing repo is private, the values appear in no other repo, and
  the credentials are scoped (one IAM user; one DNS zone). Residual
  risk accepted: anyone who ever obtains read access to the private
  `dracon-home` repo — a compromised account, a mistaken public flip, a
  shared machine with the key material — gets a working AWS key and a
  working DNS-edit token for `dracon.uk`. That is a real risk and it
  lives in a different repository than this one; rotating the AWS key
  remains the owner's call and the mechanism is already written
  (`dracon-utilities/scripts/rotate-dracon-platform-aws-key.sh`).
  This item is closed as an *accepted, recorded* risk with the
  reasoning attached — not as "the exposure was harmless".

  **What was done here so the class of leak cannot recur in this
  repo.** `scripts/secret-scan.sh` scans the tracked tree for
  credential-shaped material (AWS key IDs and secret access keys, GitHub
  tokens, PEM private-key blocks, and long literals assigned to
  secret-ish names) and fails with the file and line but never the
  value; `tests/secret_scan.rs` pins the behaviour (real shapes are
  reported, known-fake fixtures are not, the report never contains the
  secret); and the `check` job in `.github/workflows/ci.yml` runs it
  over the whole tracked tree on every push and PR. Running the same
  scanner over `dracon-home`'s tracked files finds its real credential
  files immediately, which is how the tool is meant to be used on a
  repo that does hold them. The db-gateway tree itself is clean — the
  scanner found nothing in 284 tracked files — and the full history of
  this repo contains no credential-shaped material either.*
