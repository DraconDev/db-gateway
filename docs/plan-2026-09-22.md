# db-gateway forward plan (2026-09-22 — historical, superseded)

**Document role:** Historical / superseded
**Canonical roadmap:** [`personal-turso-megaplan.md`](personal-turso-megaplan.md)
**Status:** Retained for provenance and earlier sequencing decisions. Do not use
this document to authorize or schedule future work; use the canonical roadmap
and `TASKS.md` for current sequencing and status.

## Goal

Finish db-gateway into a self-hosted Turso replacement on a single host
(micro2): hundreds of persisted databases behind one `dg` binary, operated
through the CLI, with verified backups and a safe Turso → gateway migration
path. This historical plan consolidated `TASKS.md`, the 2026-09-21 audit + tasklist,
the R1–R12 decision memos, the scale proposal, and the comparison doc into an
earlier ordered, gated sequence. The canonical roadmap supersedes its future
sequencing while preserving this document as evidence.

## Success Criteria

1. R1–R12 accepted, edited, or rejected by the owner — no live step runs on
   proposed-but-unaccepted policy.
2. D1–D3 measured on micro2; `MemoryMax`, log caps, and resource headroom set
   from numbers, not estimates.
3. Backup coverage proven end-to-end (write → off-host copy → separate-target
   restore → verified read) with visible failure signals; RPO/RTO stated as
   objectives with evidence, never as guarantees.
4. Admission bottleneck fixed per the scale proposal with before/after
   benchmarks; hundreds-of-DBs target re-tested at the new ceiling.
5. First Turso database migrated (survey → pilot → cutover with rollback
   artifacts), Turso authoritative until the cutover gate passes.
6. Every phase below lands with its stated tests green and its evidence log
   committed; live phases each have a separately approved window.

## Constraints And Non-goals

- No live action (OVH/micro2/Turso, production data, deployments,
  subscription changes) without a separately approved window — carried over
  from TASKS.md and the audit.
- No multi-host work until one host's measured post-fix ceiling is documented
  and insufficient (scale proposal Phase 4 gate).
- No automatic failover, no cross-database atomicity, no config surface for
  tuned constants until two measured sizing rounds disagree (scale proposal
  non-goals).
- PostgreSQL stays application-specific; no transparent engine
  interchangeability promise. No web dashboard unless the CLI proves
  insufficient (TASKS.md later capabilities).

## Key Decisions

- **D-a. Backup transport: gateway-native snapshots stay primary; OVH leg
  decided by the sandbox, not by assumption.** Gateway-native backup is
  already proven on micro2 (4/4 drill); TASKS.md phase 7 prescribes
  evaluating Litestream before custom code. Recommendation, executed
  within the approved Phase 2 window: put gateway-native snapshots on cron
  (cheap, proven), run the OVH sandbox runbook to decide the off-host leg
  (Litestream streaming vs snapshot upload) from sandbox numbers, and only
  then build C2/C3 freshness signals against the chosen tool — endpoints
  answering "unknown" would be fake coverage. Rejected: committing to
  Litestream before the §6 checks run; building C2 against no sidecar;
  scheduling any cron outside an approved window.
- **D-b. Scale work follows the proposal order: bounded-wait first, lanes
  second, sizing third.** The benchmark proved admission, not memory or
  SQLite, is the wall — so wait queues (Phase 1, contract-preserving, ~zero
  memory impact) come before read/write lane surgery (Phase 2). Rejected:
  jumping to lanes first (harder to validate in isolation) or to multi-host
  (no evidence one tuned host is insufficient).
- **D-c. Migration stays Turso → gateway with Turso authoritative until
  GATE 2.** Resolved in audit F1; B1 already rewrote the docs around a
  denied-SQL census, per-DB size inventory, scratch trial imports, and a
  Turso rollback floor through the soak. Rejected: any cutover without a
  write-freeze/final-export consistency mechanism.
- **D-d. Ownership lens applies to all vendor comparisons.** Caps, tiers,
  meters, regions, and token policies in Turso/D1 are business-model
  artifacts, not capability gaps (docs/evidence/comparison-2026-09-21.md §4). The
  remaining real gaps are pure engineering: hot-read scaling, WAL-granularity
  RPO, zero-loss failover. Nothing in this plan chases a managed-service
  feature that ownership makes irrelevant.

## Recommended Approach

Gated sequence, each phase executable by one session with its own evidence:
owner decisions → live measurement → backup decision+proof → admission/scale
fixes with re-benchmark → migration pilot → cutover. Local code work
(Phase 3) interleaves any time; live phases wait for their windows. Smallest
viable proof throughout: re-run the existing runbooks and benchmarks rather
than inventing new harnesses.

## Validation Plan

- Rust: `timeout 590 cargo test --workspace --locked` (wall time exceeded
  the old 280 s gate after new suites were added); `cargo fmt --all --
  --check`; `cargo clippy --workspace --all-targets --locked -- -D warnings`.
- TS: `npm test --prefix client` (7/7: typecheck + build + integration +
  lifecycle).
- Live: existing runbooks verbatim (micro2-measurement, ovh-sandbox) with
  dated evidence logs committed next to the 2026-09-21 originals; chunked
  CLI exercised in every drill (covers B2 path).
- Migration: trial-import results per source DB, GATE criteria from
  migration-cutover.md, rollback artifacts retained and listed.
- Highest-risk validation step: C1-live/Phase 2 end-to-end restore — it is
  the first proof that an off-host copy actually comes back as verified
  rows, and every later phase assumes it.

## Risks / Rollback

- Live-window risk: every live phase needs its own approval; a refused or
  interrupted window stalls Phases 1–2 but never blocks Phase 3 (local).
- Backup-tool risk: if the OVH sandbox fails adoption gates, fallback is
  documented manual validated snapshots (R1/R6 memos) — recovery stays
  honest, just slower.
- Scale-regression risk: admission changes touch the hot path; the
  proposal's per-phase acceptance (admission up an order of magnitude, p99
  within ~2× unloaded, zero non-429 errors) plus the full suite gates each
  merge. Rollback: previous binary + pre-change snapshots per the R7 memo.
- Migration risk: dual writers during cutover; mitigated by write
  freeze/final export and Turso staying authoritative until GATE 2, with the
  Turso rollback floor through the soak.
- Scope risk: TASKS.md later capabilities (TTL DBs, placement, visual
  admin) stay out unless a measured need plus approval pulls them in.
