WHAT THIS MEANS FOR THE COMPARISON — this is the richest surface and the
deepest honest gap:
1. It is READ-WRITE. "+ Add record" and the edit cells mutate the database.
   `dg` is deliberately read-only in the TUI and requires a typed statement for
   every write; `dg rows`/`dg schema` read, they never edit.
2. It offers COLUMN-VISIBILITY control ("Columns"), a SORT builder ("Sort"),
   and a FILTER builder ("Filters") as *pick-and-choose UI*. `dg rows` has the
   same three capabilities as FLAGS instead (`--sort col:desc`,
   `--where <condition>`), and the TUI as prompts (`o`, `f`, `c`). Same power,
   different ergonomics: no clickable column chooser, and filters must be typed
   as SQL conditions rather than assembled from a builder.
3. It reaches the raw source of truth directly (SQL console attached to the same
   database), where `dg` goes through its own authenticated HTTP API.
4. A type annotation per column header is shown inline. `dg schema` prints the
   declared type per column too, so this is parity, not a gap.
