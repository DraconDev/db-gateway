2026-10-27 after deploying the build to micro2 (the host behind the
127.0.0.1:7432 tunnel). Per-database exports of all 7 databases were taken
first to dist/pre-rows-2026-10-27/ with SHA256SUMS, the data dir was
copied to /var/lib/dg-pre-rows-2026-10-27, the previous binary kept as
/usr/local/bin/dg.prev-rows, and the service came back `active`.

│ 30 │ SKU-1030 │ item 30 │        1610 │   125 │ cat-2    │ 2026-10-23T10:00:00Z │

rows 1-10 of 60   sorted by stock desc   [n] next  [s] structure

The order is really the gateway's: stock 125, 112, 104, descending.

5. FILTERING — `dg rows inventory products 0 --where 'stock > 60'`:

rows 1-10 of 24   filter: stock > 60   [n] next  [s] structure

`of 24`, not `of 60`: the total is the size of the FILTERED answer, so
paging stays correct under a filter. The filter was applied in the
statement, by the gateway, not by discarding rows on the client.

6. REFUSALS — a sort column that is not a column, and a filter that
   would write:

$ dg rows inventory products --sort nosuch
{"message":"command failed","code":"invalid_arguments",
 "detail":"invalid_arguments: this table has no column named nosuch"}

$ dg rows inventory products --where "1=1; DROP TABLE products"
{"message":"command failed","code":"invalid_arguments",
 "detail":"invalid_arguments: a filter must be a read-only SQL condition,
 at most 512 characters"}

Neither reached SQL. The table was still there afterwards.

7. THE THREE AUDIT FIXES, verified live on the same gateway.

   (a) The contents are re-read on `r` and when a database is opened.
       The 30-second cadence exists to stop an IDLE view counting every
       row on every two-second poll; it is not a promise that the counts
       are fresh when the operator asks. Proven by writing a row behind
       the running view:

         view opened, tab says rows = 202
         wrote a row: server now says 203
         after pressing r, tab says rows = 203

       (The two probe rows were deleted afterwards; inventory is back to
       201 rows.)

   (b) The sort column is chosen by name, not assumed. It used to cycle
       off the first column -- on this table `id`, the rowid alias, which
       reordered nothing because the unsorted page is already in rowid
       order. Live: pressing `o` opens a prompt listing the table's real
       columns, typing `stock:desc` gives

         rows 1-10 of 60   sorted by stock desc   [n] next  [s] structure

   (c) The arrow keys and the wheel page the browser. Live: from that
       sorted first page, pressing the down arrow gives

         rows 11-20 of 60   sorted by stock desc   [p] prev  [n] next  [s] structure

       The wheel does the same; without a browser open it still scrolls
       the dashboard.
