  deadline with rollback, per-principal idempotent replay, no hidden retries.
- Lifecycle: online-backup clone/export, validated atomic import, tombstone +

## Findings

### F1. Migration direction — RESOLVED 2026-09-21 (owner)
Direction is **Turso → gateway**: db-gateway is a self-hosted Turso
replacement ("your own Turso"), operated primarily through the `dg` CLI,
and it must scale. [TASKS.md](../TASKS.md) phase 10 was right; the losers are
[docs/migration-inventory.md](migration-inventory.md) ("Turso target
group/plan", stripping `_dg_*` for the target) and
[docs/migration-cutover.md](migration-cutover.md) ("switches each
application's connection from the gateway to the target"), which describe
gateway → Turso and must be rewritten (task B1).

### F2. Databases larger than 8 MiB have no backup path (product limit)
Export/import are capped at 8 MiB decoded ([src/api.rs](../src/api.rs)
`MAX_EXPORT`, [src/main.rs](../src/main.rs) `MAX_IMPORT_BYTES`). A database
that grows past 8 MiB can no longer be exported, cloned over HTTP, snapshotted
for upgrade/rollback, or restored — every recovery story in the docs silently
stops working at that size. Either document an explicit maximum database size
or implement streaming/chunked lifecycle transfer. Do this before any
production data exists.

### F3. 688 KiB session HTML is tracked in git
`pi-session-2026-09-17T16-38-06-629Z_*.html` is committed. It's session
exhaust, not project source. Untrack it (and ignore the pattern).

### F4. `.gitignore` does not ignore likely credential files
The managed block has no `*.key` / `.env*` ignore (its `!*.key`, `!.env`
lines are no-ops without a matching ignore), so `owner.key`, `*.key`,
`.env*` files in this repo would be committed by an unaware `git add`.
Append repo-specific ignores *after* the managed block (do not edit it).

### F5. Stale strings (cheap fixes)
- [docs/api.md](api.md) title still says "(M1)" but documents M2 lifecycle + shell.
- [src/lib.rs](../src/lib.rs): module comment says execution/credentials "are
  not implemented"; `NonLoopback` message says "before authentication is
  implemented". Both are years out of date (auth shipped in M1).
- [README.md](../README.md): "Not yet available: OVH backups, HTTPS, and
  deployment" — the supervised deploy is recorded, so "deployment" is stale;
  "CI runs the Rust checks" omits the TS + validate-deploy steps CI now runs.

### F6. Small doc/behavior gaps
- `ALTER` (and temp objects/views/triggers) are denied by the authorizer but
  `ALTER` is not listed in the api.md disallowed-features set.
- Read-only principals sending `Idempotency-Key` get `400 invalid_request`
  ([src/execution.rs](../src/execution.rs)); api.md doesn't say so.
- `POST /v1/databases/{name}/import` ignores the path `{name}` except to echo
  it as `"from"`; the body `name` is the real target. Tested and harmless,
  but an odd API shape to keep forever.
- `dg list` / `GET /v1/databases` is owner-only, so scoped app keys cannot
  discover their own databases.
- Cosmetic: shell `.tables`/`.schema` filter `_dg_*` case-sensitively while
  the server protects them case-insensitively; `Store::create` counts
  tombstones toward the 1024-database cap.

### F7. Supply chain has no audit gate
No `cargo audit`/`cargo deny` in CI, no `rust-toolchain.toml` (CI floats on
stable), and `rusqlite` bundles its own SQLite C source — SQLite CVEs arrive
via dependency bumps nobody is watching. Add an audit step and a pinned
toolchain.

### F8. TS client has no typed ops surface
[client/src/index.ts](../client/src/index.ts) covers query/batch/replay only;
create/keys/clone/export/import/delete/info require raw `request()` calls.
Fine for apps, annoying for operators writing TS tooling.

### F9. Already-tracked open work (confirmed still open, not re-litigated)
Resource-budget items 1–5 unmeasured (release-blocking); Litestream/OVH
sandbox checks (§6 of [backup-compatibility.md](backup-compatibility.md))
unrun; backup-health signals design-only
([observability-contract.md](observability-contract.md)); owner decisions in
[recovery-decisions.md](recovery-decisions.md) §6 and gate 8 of
[deployment-readiness.md](deployment-readiness.md) unanswered; no owner-key
rotation story; `MemoryMax` unset; log retention undecided.

## Fixed along the way

- `tests/resource_report.rs` asserted a **global** `pgrep -f "dg serve"`,
  which flakes whenever cargo runs test binaries in parallel (any sibling
  suite's server trips it). Scoped the leak check to the harness's own
  mktemp workdir; verified passing with a neighbor server running.
- `scripts/resource-report.sh` read the server's listen address with a
  single-shot file read that races boot (no sleep, no retry) — under
  parallel-suite load the parse hit EOF first ("listen address not
  observed", two in-suite failures). Rewrote as a 30 s poll loop like the
  other harnesses; verified 3× sequential + 4× parallel.
- Full suite wall time now exceeds the old `timeout 280` gate command (new
  suites added ~60 s). Use `timeout 590 cargo test --workspace --locked`.
